# M0 measurement

Acceptance criterion from `FST-DICT-DESIGN.md` §4: compile `typey-type-full.json`
and compare the `hfstol` size and per-lookup latency against Plover's in-memory
dictionary.

`typey-type-full.json`, 145,345 entries, system `stenotype-extended`:

| | |
|---|---|
| imported | 145,340 of 145,345 |
| outlines unparseable | 0 |
| `hfstol` artifact | 6,256,925 bytes, mmap-able, zero heap |
| Plover-style resident | 93.6 MB, dict plus reverse index |
| source JSON on disk | 4,492,365 bytes |

Fifteen times smaller than the in-memory dictionary, and the kind of smaller that
matters on Android: the OS pages in what a lookup touches and nothing enters the
app heap. Reverse lookup needs no index, because inversion is a relabelling.

Compare against the JSON on disk instead and you get 6.0 MB against 4.5 MB, which
reads as a regression. That is not the criterion, and the JSON is not what a
running engine holds.

The five skipped entries are malformed in the source: four unbalanced braces
(`{{-|}^}`) and one transposed attach marker, `{,^000}` where the "thousand"
suffix means `{^,000}`.

Zero outline parse failures across all 145,345 outlines is the useful number
here. It says the greedy steno-order tokeniser agrees with Plover's everywhere,
including the hyphen and number-bar cases.

## Latency is not yet measured

20,000 probes through `hfst-optimized-lookup` take 0.17s wall, or 8.5 us each,
against 0.342 us for a Python dict lookup. That number is unusable: it includes
process startup, stdin tokenising and output formatting, not lookup. A real
comparison needs `stfst-ol`, which is one reason to write the reader rather than
wrap one.

All 20,000 probes returned a translation, so the artifact agrees with the source
on the sample.

## Two findings for the compiler

**`hfst-lexc` memory scales badly in the number of lexicons.** Delayed
alignment, expressed as one lexicon per distinct translation, needs 3.0 GB of RSS
for 10,000 entries against 40 MB for pairwise. At 145,345 entries it wants tens
of GB, and it took this machine down once. Do not express per-entry structure as
lexicons.

**Pairwise alignment shares nothing across entries.** `upper:lower` puts both
symbols on one arc, so an entry is dense but its pair sequence is unique to it.
72,012 distinct translations sit behind 145,340 outlines, so there is redundancy
the artifact does not exploit. Delayed alignment would share the translation
tails, but it needs a builder emitting ATT directly instead of going through
`lexc`. Worth measuring, and bounded above by the share of the 6.0 MB that
translations occupy.

Compile peak RSS is 898 MB for the pairwise build of typey-type.
